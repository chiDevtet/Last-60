# Operations runbook

All actions are available in the admin console (`/admin`) and the CLI (`bun run cli …`). Every
mutation is audited.

| Situation | What you see | Action |
|---|---|---|
| Payout wallet short | round `awaiting_funds`, WARN line, payout `lastError` states the asset, have/need and the amount to add (SOL, SPL token, or SOL for fees/rent) | Fund the wallet. Payouts resume automatically (retry every 5–20 s). Nothing is partially sent. |
| Payout failed after max attempts | round `attention`, ERROR line, admin "Failed payouts" | Inspect `lastError` (`bun run cli round <n>`). Fix the cause, then **Requeue** (safe: all prior attempts are provably dead). |
| Reconciliation halt | health `degraded`, "payouts halted" | Over-attribution detected. Compare `cli reconcile` output with the chain (`scripts/verify-fee-attribution.ts`). Only after explaining the difference: `cli clear-halt "<reason>"`. |
| RPC outage / 429s | indexer/rewards `degraded`, retries in logs | Automatic failover to `SOLANA_RPC_FALLBACK_URLS`. Add/replace endpoints in admin config (no restart). Rounds whose catch-up cannot complete stay `snapshotting` and resume; they never snapshot incomplete data. |
| MongoDB outage | everything `degraded`/`down` | Workers back off and resume; all writes are idempotent/conditional. No action beyond restoring Mongo. |
| Worker crash | heartbeat stale, PM2 restarts it | Nothing. A crashed snapshot resumes from its persisted slot; submitted payouts are rechecked/rebroadcast. |
| Rounds `missed` | WARN "window missed" | The engine was down for a whole final window; its buys and fees flow into the next executed round. Investigate the outage. |
| Pool graduating | WARN "Pool status is migrating/migrated", then "Pool graduated … destination verified" or "NOT verified" | Nothing to switch: a strictly verified DAMM v2 / CPMM destination is attached automatically. If NOT verified or unsupported, check `pools.migration.failed` (admin status) and `bun scripts/resolve-migration.ts`; destination activity is not accounted until verified. |
| `ALLOCATION MISMATCH` warning / round "not eligible for payout" | WARN lines, `rounds.ineligibleFees`, `FEE_EXCLUDED` ledger rows | The on-chain creator allocation differs from the declared `EXPECTED_*`, or an allocation could not be proven. Those fees are recorded but not paid. Confirm the real configuration with Forgepad; fix the declaration only if the chain is right. Historical records are never re-attributed implicitly. |
| Indexer/rewards refuse to attach: "already has fee records attributed under role …" | worker `degraded` | `FEE_BENEFICIARY_ROLE` differs from the role the pool's records were attributed under. Restore the previous role (role changes on a pool with history are not supported). |
| Unrecognised pool activity | WARN "flagged for review" | A program upgrade may have changed events. Check `anomalies` in logs; update the IDL/adapter. Unknown activity is never counted. |
| Emergency stop | — | `cli pause payouts` (stops signing; in-flight transactions still confirm), `cli pause scheduler` (no new snapshots), `cli pause indexer`. Resume with `resume`. Switching `payoutMode` to `dry_run` also stops signing of queued live payouts (they stay `pending` until live mode returns). |
| "Live payouts are queued and not being signed" | WARN line, payouts `pending` with `lastError` | Live mode is set but the rewards worker's own environment forbids signing (mainnet without `ALLOW_MAINNET_PAYOUTS=true`). Fix `.env.rewards` and restart, or switch back to dry-run. |
| Round stuck `snapshotting` with "refusing to snapshot" | `lastError` names a lagging slot or a catch-up backlog | The RPC answered from behind the previous snapshot, or the indexer is too far behind. It retries automatically; check RPC health / indexer lag. |
| Ledger check: "period fees are now X but Y were distributed" | ERROR line | Transactions arrived after a snapshot (or counted ones were dropped). Investigate the RPC/indexer around that round; the difference was not paid. |
| Revenue report shows `awaiting_distribution` / `partial` claims | `bun run cli revenue` lists the claim, its untransferred balance and distributions | A Forge LP claim has no attributed creator payout yet (Forge pays in its next step, or its payout failed and is not retried), or a creator-fee collection was not (fully) distributed. Nothing was funded for the missing part. Forge payouts are linked automatically once indexed and covered (`cli revenue-reconcile` re-runs the pass); check `funding_attributions` for the decision. |
| Forge creator distributions `pending` | report `Forge creator distributions … pending N` | Indexing coverage of the destination pool or of Forge's launch-token account has not reached the payout slot. Check the indexer is running and its `worker_state` cursors / `syncedThroughSlot` advance; nothing to do by hand. |
| Forge creator distributions `unresolved` | report reasons (`no_launch_anchor`, `forge_outflow_to_non_creator`, `previous_harvest_has_no_distribution`, `competing_distribution_since_harvest`, `asset_not_collected_by_harvest`, …) | Last-60 could not prove which single harvest the payout settles (REWARD_FUNDING.md §4a). It is recorded and never paid. Do not relabel it by hand; a decided row is never re-evaluated. |
| Unlinked funding inflows | report `unlinked funding inflows > 0` (`report:revenue` exits 2) | A transfer reached a destination but could not be tied to a claim (no memo, different mint, unknown claim). It is never funding. Fix the correlation at the source; do not relabel it by hand. |
| `excess` claims / `exceeds_policy_amount` credits | report discrepancies | More than the policy share was transferred. The excess is recorded and never paid; no action is required beyond confirming the transfer with Forge. |
| CPMM creator-fee basis `unverifiable` (`creator_fee_on` / share rate) | `verify:allocation` migration line, `cpmm_creator_fee_basis_unresolved` in rounds | The pool's `creator_fee_on` byte is not a known mode, the CreatorFeeShare override is invalid, or the spec predates PR #6. CPMM creator fees are recorded, never distributed. They are never Last-60 funding under the phase-aware policy anyway. |
| Phase-aware funding | — | `forge_phase_aware_v2` is the default policy; its activation slot is pinned at the first start of any process (`system_state.funding_policy_activation`; the boot log says when). Install the dedicated payout wallet (docs/PAYOUT_WALLET.md). To stay on the old behaviour set `REWARD_FUNDING_POLICY=legacy_creator_fee_v1` on every process. |
| Creator wallet automation | `bun run cli creator-wallet`, terminal lines "Creator wallet sent / swept …" | docs/CREATOR_WALLET.md. Idle reasons are in `rewardsWorker.blocked` (dry-run, paused, not the pool's creator, …). A low creator balance is retried automatically. A transfer with `stuckReason` reached the payout wallet but could not be recorded: it is never repeated; review it in the revenue / funding reports. |
| Rewards worker exits 78 "payout signer refused to load" | log line with a sanitized `signer.code` | `address_missing` / `malformed_key` / `address_mismatch` / `ambiguous_key_sources` / `insecure_key_file`: fix `LAST60_PAYOUT_WALLET_*` in `.env.rewards` (docs/PAYOUT_WALLET.md §2). Never "fix" it by pointing the address at another wallet. |
| Contributions "attributed, awaiting custody" | `cli funding`, admin "Contributions awaiting custody", round `fundingBreakdown.awaitingCustody` | The credited SOL is still with its custodian (the creator for Forge's payout). With the creator wallet automation this clears by itself within a pass or two once the payout is finalized (check `cli creator-wallet`). Without it: open a sweep request (`cli custody-request <fundingKey>`), send the custodian the instructions (exact lamports, payout wallet, memo `last60:custody:v1:<id>`). With the memo it binds automatically; otherwise `cli custody-submit <id> <signature>`. It funds the next round once finalized. |
| Custody submission rejected | `422` / CLI `accepted: false` with a reason; request `history` | `incorrect_source_wallet` (not from the custodian), `incorrect_destination_wallet`, `incorrect_mint` (wrapped SOL / SPL — must be native SOL), `transfer_not_after_contribution`, `custody_transaction_not_transfer_only`, `transfer_already_used`, `memo_names_another_custody_request`. The request stays open: ask for a correct transfer. Funds sent wrongly are not credited (they may still sit in the payout wallet as unattributed surplus). |
| Custody `partial` / `excess` | custody row `reconciliation` | Partial: open a new request for the outstanding remainder (shown on the request). Excess: only the outstanding amount is credited; the excess is unattributed wallet balance. |
| Custody `awaiting_finality` that does not clear / `failed` | custody row `confirmationStatus` | It is promoted by every reconciliation pass (`cli custody-refresh`). `failed` = the transaction failed or never finalized: nothing was credited; open a new request. |
| Custody liquidity `mismatch` | `custody` reconciliation report, WARN line, admin "Actual payout liquidity" shortfall | The payout wallet holds less than custodied-unconsumed contributions + pending payouts + reserve. Someone moved SOL out of the payout wallet, or a payout is in flight. Investigate before resuming payouts; never mark contributions as available by hand. |
| An unresolved Forge attribution may now be provable (e.g. a missing harvest was backfilled) | report `unresolved` reasons such as `no_preceding_harvest` | With `LAST60_ATTRIBUTION_RECOVERY_ENABLED=true`: confirm `cli status` cursors cover the payout slot, then `cli recover <attributionKey> "<why>"` (or admin "Re-run verification"). It re-runs the unchanged algorithm; outcome `linked` / `linked_not_payable` / `still_unresolved` / `rejected` is recorded in `cli recoveries`. Never edit `funding_attributions` or `reward_funding` by hand. |
| Change reward parameters | — | Admin config. Applies from the next snapshot; each round stores the config it used. |
| Switch provider / pool | — | Admin config (critical: needs confirmation + reason). The indexer re-attaches and ingests the current reward period. |
| Rotate payout key | — | docs/PAYOUT_WALLET.md §8: only with no custodied-unconsumed contribution and no open custody request; pause payouts → wait until no payout is `submitted` → swap key file and `LAST60_PAYOUT_WALLET_ADDRESS` (every process) + admin `expectedPayoutPublicKey` → restart → resume. |
| Rotate schedule key | — | Only between rounds' final windows: restart `last60-rewards` with the new key **before** the next window opens (old ciphertexts are only needed for the current round). |

## Routine checks

* Daily: `bun run cli status`, `bun run cli reconcile`, `bun run cli revenue`, `bun run cli funding`,
  `bun run cli payout-wallet`, spot-check a round with `scripts/verify-round.ts`.
* Keep the payout wallet funded for at least a day of rewards plus fees.
* Back up MongoDB; test restores.
